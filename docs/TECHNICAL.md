# UAC2 Control 技术说明

[English](TECHNICAL.en.md) · [中文使用说明](../README.md)

本文对应 Windows x64 版 0.2.2。UAC2 Control 修改 Windows 为某个播放输出公布的 **WASAPI 共享模式最小周期**。周期是共享音频引擎每次处理一批音频帧的时间，一帧包含同一时刻各声道的一个样本。48 kHz 下，480 帧为 10 ms，144 帧为 3 ms。降低下限后，主动请求短周期的应用才有机会采用它。继续请求默认周期的应用仍可使用 480 帧。

| 读数 | 来自哪里 | 可以判断什么 |
| --- | --- | --- |
| 已公布下限、默认及步进 | Windows 对当前共享混音格式的周期查询 | 该格式允许请求的范围和间隔 |
| 当前周期 | Windows 共享音频引擎的运行读数 | 读取时实际运行了多少帧。已有播放流可能影响结果 |
| 试流队列等待（~ms） | 独立静音流中，音频库报告的排队字节数 | 新音频前面已有多少待播放音频，换算为估算时间 |

Windows 按格式公布可请求的引擎周期。BASSWASAPI 的队列读数还可能包含设备或驱动报告的额外等待，因此换算出的毫秒数可以超过单个引擎周期，甚至超过库所分配的缓冲时长。[微软周期接口说明](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient3-getsharedmodeengineperiod) · [BASSWASAPI 队列读数说明](https://www.un4seen.com/doc/basswasapi/BASS_WASAPI_GetData.html)

要得出按键到耳机出声的端到端延迟，还须测量输入、应用处理和实际声输出。程序没有采集这些时间点。WASAPI 独占、ASIO 及录音不在本工具调整范围内。[Windows 音频读取](../src/devices/audio.rs) · [试流实现](../src/benchmark.rs)

## 从播放端点找到驱动

枚举对象是活动播放端点，即用户在 Windows 中能分别选择的输出。同卡的耳机和 S/PDIF 可以有不同的端点 ID。默认输出只影响列表排序。程序从端点的即插即用节点向上找音频功能及物理 USB 设备，核对 VID/PID、三层容器 ID、运行状态和本次到达时间。音频功能须同时绑定 `usbaudio2` 服务、`Microsoft` 提供商和 `usbaudio2.inf`。确认操作时重新比对身份，拔插、换驱动或格式改变都可能使旧确认失效。[端点枚举](../src/devices/audio.rs) · [USB 身份](../src/devices/pnp.rs) · [各操作的匹配条件](../src/devices.rs)

权限和能力分别判断。**修改**还须能读取设备输出格式、共享混音格式和公布周期，并在提交时通过记录校验。**试流**只需可核对的共享混音格式及周期范围，厂商驱动、板载或 HDMI 输出也可能符合。**强制恢复**依赖可核实的活动微软 UAC2 音频功能，因此即使能力表、周期或快照不可读，也能尝试重建。[端点检查](../src/devices/audio.rs) · [恢复入口](../ui/main.js)

## 能力记录和修改范围

实现通过所选端点的 Windows 属性存储读写 `{a2a3fff4-353f-407c-9d86-1f9dc7d5a606},2`（PID 2），并独立读取注册表中的持久化副本。解析器依据设备采集样本识别版本 10、单一已知处理模式和有界的格式表。每行包含步进、默认、最小、最大等帧数和对应的波形格式。写前需要 Windows 的设备输出格式字节与某条已知 PCM 行完全匹配，输出和混音的声道数、采样率须吻合。[属性读写](../src/profile/native.rs) · [表结构与格式校验](../src/profile/capability.rs)

- **当前采样率**覆盖此端点当前声道数、当前采样率下所有符合条件的整数 PCM 行，可能有多个位深。
- **全部采样率**在同一端点、相同声道数下，覆盖 44.1、48、88.2、96、176.4、192、352.8、384 kHz 中实际存在的行。可识别的有效位深为 16、24、32 位，24 位支持三字节和四字节容器。
- 每行先将目标毫秒数换算为帧并向上取整，再向上对齐到该行步进。某行目标超过它自己的原默认值时，整项修改停止。每条匹配记录只更新最小帧数字段，保留原默认、步进、最大和格式。选 3 ms 时，44.1 kHz、步进 1 的结果是 133 帧，48 kHz 是 144 帧。[候选生成与离线断言](../src/profile/capability.rs)

写入针对一个播放端点。为让 Windows 重新加载，程序随后请求重启整块物理 USB 设备，同卡播放和录音都可能中断。对可读的同功能其他活动播放端点，会对照操作前后的能力正文、格式和公布周期。切换位深或采样率后，需查新格式的实读数。某条记录写入成功并不能证明相应格式已开流。[配置、同卡对照与重载](../src/profile.rs)

## 写前保护与待重载状态

1. 在设备和本次 USB 连接核实后，读取属性正文及注册表副本。已知副本由 8 字节前缀和相同正文组成，前缀须符合 `41 00 xx xx 01 00 00 00`。正文长度及每一个字节均需一致。首次修改前保存原始正文与持久化原件，以后沿用首份快照。
2. 比对当前格式的能力行和 Windows 公布的范围。若有未完成的重载，只能接受该快照中可解释的原始、操作前或目标状态。遇到外部改写、未知布局、长度或范围冲突即停止。
3. 修改前先记下本次原件、目标和待重载标记。打开可写属性存储后，再比对两份原件。此时连前缀中允许变化的两个字节也须与本次首次读取一致。用 `SetValue` 和 `Commit` 提交，再重新打开并独立读回。
4. 普通重启后核对设备、驱动、格式、完整目标正文及当前格式的公布范围。重启返回 3010 时，即便当前格式符合目标，也会保留待重载状态，因为其他格式是否已重载仍不能确认。只有通过重载验证才清除标记。点击刷新可以重新读 Windows 当前的公布值和运行值。[修改流程](../src/profile.rs) · [提交与独立读回](../src/profile/native.rs) · [快照](../src/profile/store.rs)

### Windows 10 样本

CX31993 HiFi Audio 的早期故障报告来自 Windows 10 22H2、19045.6466，驱动 `usbaudio2.inf` 10.0.19041.1，双声道 32 位／48 kHz。两次只读采集的注册表记录都是 936 字节，前缀为 `41 00 35 00 01 00 00 00`，其余 928 字节与端点属性完全一致。0.1.0 把该前缀误判为未知，写前即停。该格式的原始记录为最小 336 帧、默认 480 帧、步进 1 帧、最大 480 帧。

公开样本可离线验证 3 ms 目标在该频率命中 3 行，在全部范围命中 5 个频率、15 行，以及恢复候选能还原完整正文。前缀中其他取值、正文损坏和提交前原件改变另有合成用例。后来用户确认这台 Win10 CX31993 已可用，未随反馈提供复测版本、截图、逐项读数或恢复日志。上述帧数属于原始诊断。[Win10 样本](../src/profile/fixtures/win10_pid2.json) · [回归用例](../src/profile/compatibility_tests.rs)

## 三种恢复操作

| 操作 | 条件和作用 | 完成的判据 |
| --- | --- | --- |
| 恢复原厂默认设置 | 将所选端点的整份能力正文还原到本工具首次修改前，覆盖当时保存的各采样率。若使用前已有其他自定义值，它们也会还原。快照须匹配端点、USB 实例、容器及驱动版本，现场正文须与它记录的已知状态一致。 | 独立读回与重载核对和常规写入相同。快照缺失或无法核实时，界面说明原因，可另行确认强制恢复。 |
| 硬重启 | 仅当完整已写入正文与待重载目标一致时可用。确认后对核实的集线器端口请求一次重连，取消则保留待重载记录。 | 重新枚举后核对原端口、原端点 ID、驱动、格式、完整记录、公布范围及运行周期，再清除标记。端点 ID 变化时，旧快照仍绑定原 ID。 |
| 强制恢复 | 经单独确认，Windows 卸载指定 USB 音频功能的设备实例，保留驱动包，再重新识别。若未返回，可对先前核实的端口尝试一次重连。同卡音频可能中断，端点 ID、音量或默认输出可能改变。 | 依据设备、驱动和连接器重新识别输出。换 ID 只接受操作前后均可唯一对应的连接器。重新识别成功后单独报告能否核对周期。 |

重启或重连前请暂停播放、降低音量。低于 3 ms 时界面会额外提醒断音、爆音或无声风险。WebView2 Runtime 或其缓存无法使用时，程序可打开原生应急窗口，选择核实过的音频功能并再次确认强制恢复。驱动拒绝、端口无法唯一定位、设备离线都会限制恢复能力。[恢复实现](../src/profile.rs) · [端口匹配](../src/profile/port.rs) · [原生应急窗口](../src/emergency.rs)

## 静音试流与估算方法

**为什么使用 osu!（lazer）随附的两份库？** 在所引版本的 osu-framework 中，游戏启用实验性 WASAPI 输出时，BASSWASAPI 的回调从游戏总混音器取出已混好的声音。它以共享事件模式开流，使用 `EventDriven` 和 `AutoFormat`，缓冲参数为 0，并以 `float.Epsilon` 请求最小周期。UAC2 Control 用本地 BASS 和 BASSWASAPI 模拟从这里往后的输出过程。例如，打击音已混好并进入队列，前面还有多少毫秒的音频要先播完？助手用独立的全零回调估算这段等待，并请求不同周期作对照。它跳过游戏逻辑、混音及按键处理，实际出声时刻也未采集。这个对照适用于游戏选择这条输出路径时。[上游 WASAPI 分支](https://github.com/ppy/osu-framework/blob/932a5529e34eb8a0f993d51f3c3d501faf921055/osu.Framework/Threading/AudioThread.cs#L123-L137) · [上游回调和初始化参数](https://github.com/ppy/osu-framework/blob/932a5529e34eb8a0f993d51f3c3d501faf921055/osu.Framework/Threading/AudioThread.cs#L207-L253) · [本工具的静音回调和开流参数](../src/benchmark/library.rs)

主程序是单个 EXE，清单使用 `asInvoker`。从普通桌面启动时，它通过 `runas` 请求管理员权限，以便写入端点属性和执行设备重启或重建。实际加载游戏音频库的助手使用普通用户权限。首次启动的使用风险同意、每次设备操作的确认和手动开始试流是三个独立步骤。[程序清单](../build.rs) · [桌面入口](../src/main.rs)

用户选择本地 osu!（lazer）安装目录或其 `current` 子目录，程序校验 `bass.dll`、`basswasapi.dll` 的 x64 格式和 Windows 信任的 Un4seen 签名。目录准备好之后，仍需点击「开始测试」。主窗口通过普通桌面 Explorer 启动同一 EXE 的非提升权限助手，双方核验命名管道对端。助手在受限搜索目录中加载 DLL，检查 2.4 系列接口及所需导出。发行包不含这两份库。整个工具修改的是系统端点设置，试流读取用户提供的库并在助手内执行，不操作游戏进程。对特定游戏反作弊系统未作认证。普通用户权限仍允许本机原生 DLL 访问该账户有权访问的资源。使用其他管理员账户输入凭据的启动路径尚缺真机验收。[提权入口](../src/main.rs) · [助手与通信](../src/bench_worker.rs) · [库加载](../src/benchmark/library.rs) · [签名校验](../src/benchmark/library/trust.rs)

1. **锁定条件。** 使用所选端点 ID、共享混音格式和已生效的周期范围。试流通过 BASSWASAPI 打开共享事件流，各档回调发送全零样本，保留现有系统音量、静音和持久配置。未应用的滑条值不参与对照。其他程序仍可能在同一输出上播放。
2. **三档请求。** 第一档通常使用默认周期。默认偏离 10 ms 且公布范围允许时，显式请求 10 ms，否则使用实读默认。第二档请求 7 ms 对照，第三档请求已公布的最小周期。7 ms 只有在该设备、该格式原始记录可核实时才可称为原下限。每轮重新按端点 ID 打开输出，并以 Windows 的运行帧数确认请求。
3. **采样。** 每个可测档做 10 轮。每轮预热约 250 ms，以变化的间隔取 97 次 `BASS_WASAPI_GetData(NULL, 0)` 的排队字节数。共享浮点流每声道每样本 4 字节，队列毫秒数 = 排队字节数 × 1000 ÷（声道数 × 4 × 采样率）。轮内检查 Windows 运行周期是否变化，并核对回调帧长。先取每轮中位数，再取 10 轮中位数。
4. **可比性。** 一档须取得十轮有效且相同的实际周期。无法开流、运行周期与请求不符或条件改变时报告原因。两档实际周期相同则标「同一周期」。其余可比档位以对照队列减去当前队列。负值表示当前档测得更慢。结束或取消后释放流，复核设备、格式和公布范围。如果还有其他客户端，空闲时的运行周期可以随它们改变。[请求、取样与汇总](../src/benchmark.rs) · [回调与队列读取](../src/benchmark/library.rs)

## 本地数据、构建与复核

EXE 旁的 `uac2-data/private/settings.json` 按当前 Windows 账户保存同意状态、语言、主题和游戏路径。`device-recovery.json` 保存首次快照和待重载状态，与 `recovery.integrity.json` 一同备份。这些私有文件通过 Windows 访问控制和原子更新保护。完整性校验能发现单份文件损坏或两者不匹配，将整套文件一起退回旧备份则无法检出。旧机器级设备快照可独立迁移。0.2.1 对旧注册表偏好只沿用可识别的语言和主题。普通启动不追加诊断日志。[偏好](../src/preferences.rs) · [本地存储](../src/data.rs) · [旧快照迁移](../src/profile/store.rs)

0.2.1 的发行 EXE 曾保留 81 处绝对构建路径，对应依赖缓存中的 56 个源码文件。0.2.2 构建脚本在编译时重映射本机构建路径，并在 Build 与 Package 阶段检查实际二进制文件。命中已知本地根目录或绝对 Cargo 依赖源码路径时，脚本会停止。[构建路径检查](../build.ps1)

独立核对一台设备时，在已提升的终端运行 `UAC2-Control.exe --inspect` 可获取活动端点 JSON。先记录所选输出、驱动、格式、下限、默认和当前周期。仅在准备中断该声卡时应用目标、查看「Windows 实读」并和原值对照。要证明短周期能实际运行，再在同一格式下手动试流。在主窗口完成风险确认后，也可用 `UAC2-Control.exe --measure "<端点 ID>" "<音频库目录>"` 开始实际试流并取得逐轮 JSON。需验证恢复时，用同一格式核对首次快照的下限、默认及待重载状态，同时检查同卡其他输出。
