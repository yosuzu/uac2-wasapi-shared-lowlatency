# UAC2 Control technical reference

[中文版](TECHNICAL.md) · [English user guide](../README.en.md)

This document describes version 0.2.3 for Windows x64. UAC2 Control changes the **minimum WASAPI shared-mode engine period** that Windows advertises for a playback output. An engine period is the time between batches of audio frames. Each frame contains one sample per channel. At 48 kHz, 480 frames represent 10 ms and 144 frames represent 3 ms. A lower minimum lets a client request shorter periods. A client that requests the default can still run at 480 frames.

| Reading | Source | What it tells you |
| --- | --- | --- |
| Published minimum, default and fundamental period | Windows engine-period query for the current shared mix format | The periods a client can request and the increment between them |
| Current period | Windows shared engine at the time of the query | How many frames the engine is actually processing per period. Existing streams may affect this reading. |
| Estimated queue wait (~ms) | Bytes reported as queued on the separate silent test stream | How much audio is already ahead of new audio, expressed as time |

Windows reports the available engine periods for a particular format. The BASSWASAPI queue reading may include extra latency reported by the device or driver, so its time estimate can exceed one engine period or even the duration of the library's allocated buffer. [Microsoft engine-period reference](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient3-getsharedmodeengineperiod) · [BASSWASAPI queue reading](https://www.un4seen.com/doc/basswasapi/BASS_WASAPI_GetData.html)

Measuring keypress-to-headphone latency would also require timestamps for input, application processing and physical sound output. This tool collects none of those timestamps. Its adjustments are confined to shared playback and exclude WASAPI exclusive mode, ASIO and recording. [Windows audio queries](../src/devices/audio.rs) · [Stream measurement](../src/benchmark.rs)

## Identifying the playback endpoint and driver

An active playback endpoint is one output the user can select in Windows. Headphones and S/PDIF on the same card can have different endpoint IDs. The system default affects list ordering. Starting at the endpoint's Plug and Play node, the program locates the audio function and physical USB device. It checks the USB vendor/product identifiers, the container ID across all three nodes, device status and arrival time. The function must use service `usbaudio2`, provider `Microsoft` and INF `usbaudio2.inf`. The program rechecks identity when the user confirms an operation. Reconnection, driver changes or a new format can invalidate a previous confirmation. [Endpoint enumeration](../src/devices/audio.rs) · [USB identity](../src/devices/pnp.rs) · [Operation-specific comparisons](../src/devices.rs)

**Adjustment** also requires a readable device format, shared mix format and published periods, followed by capability validation at write time. **Measurement** requires a verifiable shared mix format and period range. Outputs using vendor drivers, onboard audio or HDMI may qualify. **Force restore** requires a verified active Microsoft UAC2 function and can remain available when the capability table, periods or snapshot cannot be read. [Endpoint inspection](../src/devices/audio.rs) · [Recovery controls](../ui/main.js)

## Capability record and write scope

The program accesses property `{a2a3fff4-353f-407c-9d86-1f9dc7d5a606},2` (PID 2) through the selected endpoint's Windows property store. It independently reads the persisted registry copy. The parser recognizes version 10, one known processing mode and a bounded table of formats observed in device captures. Each row contains a frame increment, default, minimum, maximum and its wave format. The current device format must match the bytes of a known PCM row. The device and mix formats must agree on sample rate and channel count. [Property access](../src/profile/native.rs) · [Layout and format checks](../src/profile/capability.rs)

- **Current sample rate** covers every recognized integer PCM row on that endpoint with the current channel count and rate. This can include several bit depths.
- **All sample rates** covers existing rows on that endpoint with the same channel count at 44.1, 48, 88.2, 96, 176.4, 192, 352.8 or 384 kHz. Recognized valid bit depths are 16, 24 and 32 bits. A 24-bit sample can occupy a three- or four-byte container.
- For each row the program converts milliseconds to frames, rounds up and aligns upward to its frame increment. If any selected row would exceed its own default, the whole change stops. Each eligible row retains its format, default, maximum and increment. Only its minimum changes. With a one-frame increment, 3 ms yields 133 frames at 44.1 kHz and 144 frames at 48 kHz. [Candidate generation and assertions](../src/profile/capability.rs)

The write targets one playback endpoint. Reloading requests a restart of its physical USB device, which may interrupt other playback and recording on the card. Where readable, the program compares the capability bytes, formats and published ranges of other active playback endpoints on the same audio function before and after the operation. After changing sample rate or bit depth, check the new format's readings. Writing a row alone cannot establish that a stream has run at that format. [Configuration, sibling checks and reload](../src/profile.rs)

## Safeguards and pending reloads

1. After checking the device and USB connection, read the endpoint property and its persisted registry copy. The recognized registry representation has an eight-byte prefix matching `41 00 xx xx 01 00 00 00`. The remaining bytes must match the property exactly, including length. Preserve the original property and registry value before the first change and retain that first snapshot across subsequent changes.
2. Compare the active format's capability row with the Windows published range. During a pending reload the observed range must be explained by the original, pre-operation or intended state in the snapshot. External changes, unknown layouts, length mismatches and unexplained ranges stop the operation.
3. Save the pre-operation value, intended bytes and pending flag. After opening the writable property store, check both original values a second time. Even the two variable prefix bytes must still match the first read of this operation. Submit through `SetValue` and `Commit`, then reopen and read back independently.
4. Following the ordinary restart, check the device, driver, format, entire intended payload and current format's published range. A restart result of 3010 keeps the operation pending even if the active format matches, since the reload of the other formats has yet to be confirmed. Clear the flag only after verification. Refresh in the UI rereads the Windows published and current values. [Configuration sequence](../src/profile.rs) · [Commit and independent readback](../src/profile/native.rs) · [Snapshot storage](../src/profile/store.rs)

### Windows 10 capture

The original CX31993 HiFi Audio report came from Windows 10 22H2 build 19045.6466, `usbaudio2.inf` driver 10.0.19041.1, stereo 32-bit/48 kHz. Two independent reads returned the same 936-byte registry value, beginning with `41 00 35 00 01 00 00 00`. The remaining 928 bytes matched the endpoint property exactly. Version 0.1.0 rejected the prefix before writing. The original row advertised a minimum of 336, default of 480, increment of 1 and maximum of 480 frames.

The public fixture allows an offline check that a 3 ms request selects three rows at the current rate or fifteen rows across five rates, and that snapshot restoration recovers the entire original payload. Synthetic cases cover other prefix values, body corruption and changes between the initial read and commit. The user has since confirmed that the tool works on this Windows 10 CX31993. That update did not include a retest version, screenshot, per-operation readings or recovery log. The figures above come from the original diagnostic capture. ## What the three recovery actions do

| Action | Preconditions and effect | Verification |
| --- | --- | --- |
| Restore factory defaults | Restores the selected endpoint's entire capability payload from before this tool's first change, including all rates in the snapshot. Pre-existing customizations are part of this baseline. The snapshot must match the endpoint, USB instances, container and driver version. The live payload must match a state known to that snapshot. | Uses the same independent readback and reload checks as a normal write. A missing or unverifiable snapshot leads to an explanation and an option to confirm force restore separately. |
| Hard restart | Available when already-persisted bytes match the entire pending target. Confirmation requests one reconnection on the verified hub port. Cancellation preserves the pending record. | After re-enumeration, checks the original port and endpoint ID, driver, formats, entire record, published range and running period before clearing the flag. If the endpoint ID changes, the snapshot remains bound to the old ID. |
| Force restore | After separate confirmation, Windows removes the selected USB audio function's device instance, keeps the driver package and rediscovers the function. If it fails to return, the tool may attempt one reconnection on the previously verified port. Audio on the card may stop, and the endpoint ID, volume or default output may change. | Matches the returning output by device, driver and connector. A new ID is accepted only if the connector can be uniquely matched both before and after the operation. The result reports separately whether the periods could be read. |

Pause playback and lower the volume before restarting or reconnecting. Below 3 ms the interface also warns about dropouts, pops and silence. If WebView2 Runtime or its cache is unavailable, a native recovery window can select a verified audio function and obtain a second confirmation for force restore. Driver rejection, an ambiguous port or an offline device can prevent recovery. ### Audio activity and snapshots during force restore

After confirmation, the tool checks for playback and recording on the selected card. An active stream or an inconclusive check stops the operation before Windows removes the device. Muting a player can leave its stream running. Stop playback or recording, close the application if necessary, and confirm again for a fresh check. Another application can still open a stream after the check. [Windows audio session states](https://learn.microsoft.com/windows/win32/api/audiopolicy/nf-audiopolicy-iaudiosessioncontrol-getstate)

Once Windows rediscovers the card, the tool checks the snapshot for the verified returning output. If that output has no snapshot, the tool checks its format, published periods, capability records and persisted copy, then saves the settings Windows rebuilt for use with ordinary restore. It preserves any original snapshot already on file. If the snapshot cannot be verified or saved, the result reports that separately from the device's return. [Recovery implementation](../src/profile.rs)

If Windows returns `3010` during removal or the targeted device scan, restart Windows and refresh the device list. This code means the system requires a reboot to complete the operation. The tool stops at that step and preserves any existing snapshot. [Microsoft PnPUtil return values](https://learn.microsoft.com/windows-hardware/drivers/devtest/pnputil-return-values)

## Silent stream and queue estimate

**Why use the two libraries from osu! (lazer)?** In the referenced osu-framework revision, enabling the game's experimental WASAPI output makes its BASSWASAPI callback fetch mixed audio from the game's global mixer. It opens an event-driven shared stream with `EventDriven`, `AutoFormat`, a buffer argument of zero and `float.Epsilon` to request the minimum period. UAC2 Control uses local BASS and BASSWASAPI to model the output stage from that point forward. For example, once a mixed hitsound joins the queue, how much audio has to play before it? A separate callback supplies zero-valued samples so the helper can estimate that wait and compare requested periods. It skips game logic, mixing and input processing, and does not observe physical sound output. The comparison applies when a game uses this output path. [Upstream WASAPI selection](https://github.com/ppy/osu-framework/blob/932a5529e34eb8a0f993d51f3c3d501faf921055/osu.Framework/Threading/AudioThread.cs#L123-L137) · [Upstream callback and initialization](https://github.com/ppy/osu-framework/blob/932a5529e34eb8a0f993d51f3c3d501faf921055/osu.Framework/Threading/AudioThread.cs#L207-L253) · [Test callback and stream parameters](../src/benchmark/library.rs)

The program ships as one EXE with an `asInvoker` manifest. From an ordinary desktop it requests elevation through `runas` so the main process can write endpoint properties and restart or rebuild devices. The helper that loads the audio libraries runs without elevation. First-run risk acceptance, confirmation of individual device operations and manually starting a test are separate steps. [Manifest](../build.rs) · [Desktop entry point](../src/main.rs)

The user selects a local osu! (lazer) installation or its `current` directory. The program checks the x64 format and Windows-trusted Un4seen signatures of `bass.dll` and `basswasapi.dll`. Selecting the directory prepares the test. Clicking **Start test** launches a non-elevated instance of the same EXE through desktop Explorer. Both processes check their named-pipe peers. The helper loads the DLLs with a restricted search path, checks their 2.4 API generation and resolves required exports. The distribution excludes those two libraries. The tool configures a Windows audio endpoint. The helper loads local audio libraries in its own process and does not access the game process. There is no certification for any particular anti-cheat system. Native DLLs can access resources available to the ordinary user. Elevation using another administrator's credentials still lacks a hardware acceptance run. [Elevation](../src/main.rs) · [Helper and IPC](../src/bench_worker.rs) · [Library loading](../src/benchmark/library.rs) · [Signature verification](../src/benchmark/library/trust.rs)

1. **Fix the conditions.** Use the selected endpoint ID, shared mix format and applied period range. BASSWASAPI opens a shared event-driven stream. Its callback sends zeros, preserving system volume, mute and persistent settings. An unapplied slider value does not affect the comparison. Other applications can continue playing on that output.
2. **Request three periods.** The first band normally uses the default. If the default differs from 10 ms and the published range allows a 10 ms request, request 10 ms explicitly. Otherwise use the reported default. The second band requests the 7 ms reference, and the third requests the published minimum. Establishing 7 ms as a device's original minimum requires its original record for that format. Each round reopens the output by endpoint ID and checks the running frame count reported by Windows.
3. **Sample the queue.** Each measurable band gets ten rounds. After approximately 250 ms of warm-up, each round collects 97 queue-byte readings from `BASS_WASAPI_GetData(NULL, 0)` at varying intervals. With four bytes per channel sample in the floating-point stream, estimated queue milliseconds = queued bytes × 1000 ÷ (channels × 4 × sample rate). The program checks the Windows running period during sampling and compares callback length in frames. It takes the median within each round, then the median across ten rounds.
4. **Compare like conditions.** A band requires ten valid rounds at the same actual period. Stream initialization failures, a period different from the request or changed conditions yield a reason. If two bands run at the same frame count, they are reported as the same period. For comparable bands, subtract the current queue from the reference queue. A negative difference indicates a slower measured result. Completion and cancellation release the stream and recheck identity, format and published range. Other clients may change the running period once the test closes. [Requests, sampling and aggregation](../src/benchmark.rs) · [Callback and queue read](../src/benchmark/library.rs)

## Local data, building and independent checks

Next to the EXE, `uac2-data/private/settings.json` stores consent, language, theme and game path per Windows account. Back up `device-recovery.json`, which holds first-use snapshots and pending states, together with `recovery.integrity.json`. Private files use Windows access controls and atomic updates. The local integrity check detects individual file corruption or mismatched files. Restoring an entire matching older set is outside that check's coverage. Legacy machine-wide device snapshots migrate separately. Version 0.2.1 imports recognized language and theme values from old registry preferences. Normal startup does not append diagnostic logs. [Preferences](../src/preferences.rs) · [Local storage](../src/data.rs) · [Snapshot migration](../src/profile/store.rs)

On Windows x64, install stable Rust for MSVC, the Visual Studio x64 C++ tools and a Windows SDK. The main interface needs WebView2 Runtime. Run the relevant commands from the repository root. The Node.js UI tests also require Playwright and Chromium. `UAC2_PLAYWRIGHT_MODULE` and `UAC2_BROWSER_PATH` can point to existing installations. [Build script](../build.ps1) · [UI tests](../tests/ui.test.cjs)

```powershell
./build.ps1 -Mode Test
node --test tests/ui.test.cjs
./build.ps1 -Mode Build
./build.ps1 -Mode Package
```

The default Rust tests use public fixtures to check format selection, prefix variants, independent-readback preconditions, snapshot restoration and pending state. The UI suite uses simulated devices. Tests that interrupt a physical device are ignored by default. Build produces `dist/UAC2-Control.exe`. Package produces a ZIP with the EXE, license and third-party notices in `target/packages`. [Offline compatibility tests](../src/profile/compatibility_tests.rs) · [Explicit hardware tests](../src/profile/live.rs) · [Distribution notices](../THIRD-PARTY-NOTICES.txt)

The 0.2.1 release executable contained 81 occurrences of absolute build paths referring to 56 source files in the dependency cache. The 0.2.2 build script remaps local paths during compilation and inspects the resulting binary in both Build and Package modes. It stops if it finds a known local build root or an absolute Cargo registry source path. [Build path checks](../build.ps1)

For an independent device check, run `UAC2-Control.exe --inspect` from an elevated terminal to obtain active endpoint JSON. Record the selected output, driver, format, minimum, default and current period. When it is acceptable to interrupt the device, apply a target and compare the Windows readback with the baseline. To establish whether a short period actually runs, start a stream test in that same format. After accepting the main window's risk prompt, `UAC2-Control.exe --measure "<endpoint ID>" "<audio library directory>"` runs the actual test and emits per-round JSON. To verify restoration, use the same format to compare the minimum, default and pending state with the original snapshot, and check the other outputs on the card.

For an issue, select the affected output and generate the diagnostic report manually. The probe updates `uac2-data/diagnostics/latest.json` with the application and Windows versions, driver, format and periods. Where applicable, it reads the capabilities twice and records lengths, prefixes, the first difference and the original/intended ranges. Review this file before attaching it. Include the device model, requested milliseconds, scope, exact message, other playback at the time and whether failure occurred on write, reload or stream initialization. Keep private preferences and recovery snapshots local.
